Title: SD and AI Agents: the Guide, the Knowledge Pack and the Skill
Subtitle: What an AI agent is given to work in SD, how it is kept true, and the one rule that does not bend: the gates are walls.

An AI agent (Claude Code, or any tool that reads files) that is asked to write SD BASIC meets a language that looks like OpenQM, UniVerse or D3 and is not. It guesses names that SD lacks, and the compiler's answer to a missing function is a complaint about a matrix nobody declared. This page describes what the source repository holds to prevent that. **It holds documents and a generator. It does not connect an agent to SD, it holds no key and it calls no model.** The folder is `sdb_ai/sd64/agent-pack/` of the SD Core for Linux source repository. The installer copies two parts of it, as text, to `/usr/local/sdsys/agent-pack/`: the guide and the pack (not the skill, the templates, the recipe or the generator). They are owned by `sdsys` and no SD user can write them, they are the description of the installed version (the installer skips the copy, with a note, if the download's pack is for another version), and an ordinary account cannot read them from inside SD, because a path outside the account needs `os-on`. They are there for the administrator to copy to the machine where an agent runs.

## What is in it

| | |
|---|---|
| **The guide** (`guide/sd-basic-guide.md`) | about eight thousand words: the language, the system around it, and what SD does not have, with twenty-odd worked programs. Every block in it is compiled by `gplbld/sandbox-guide.py` on a private SD, every `run` block is run and must print what the guide says, and every line of the guide's table of missing names must still fail to compile, so that the day SD gains one the guide fails its own test. A sentence with no probe is marked `[unverified]` |
| **The knowledge pack** (`pack/`) | generated by `mkpack.py` from the sources: one chunk for each TCL verb and query keyword, VOC record type and layer, dictionary item type, format and conversion code, BASIC statement, function, `$mode` and `option`, message, account word, `sd.conf` setting and key constant, with the file and line each came from. Real VOC records and real dictionary items are quoted verbatim |
| **The skill** (`skill/sd-core/`) | a Claude Code skill: `SKILL.md` and, under `references/`, the guide and the pack. An agent that is installed with it reads the guide first and looks items up by chunk id |
| **A CLAUDE.md template and the recipe** | for a project that lives in an SD account, and for giving the agent an account of its own. The recipe is described for the administrator in [Giving an AI Agent an Account](18-the-agent-account.html) |

## How it is kept true

The pack is not typed. Its rosters are computed: a verb is a VOC record of type `V`, a message is a file, a statement is a name in the compiler's tables, a setting is a branch of the configuration reader. Meaning that no program can state (what a query keyword does) is quoted from this documentation by heading, and the generator **refuses to write** if a heading it needs has gone or a verb has no syntax line. The free check `gplbld/test-pack-units.py` regenerates the pack and fails if it differs from the committed one, if a verb or message has no chunk, if a cited message does not exist, or if the line a chunk cites has changed. `gplbld/sandbox-pack-examples.py` then checks the pack against a running SD: the verbs, the shipped VOC records and the shipped dictionary items must be what the pack says, and `create.account` and `modify.account` must print the syntax it quotes.

A change to a verb, a message, the compiler's tables, a documentation section the pack quotes or the guide turns the check red until the pack is regenerated and the difference read:

```
python3 sdb_ai/sd64/agent-pack/mkpack.py --write
```

The line numbers in a chunk's `src=path:line#hash` are locators that may lag after an edit elsewhere in the same file; the eight-digit hash of the cited line is what is held.

## The rule that does not bend

The gates (ssh, API, `sh`, `os.execute`, saving to a VOC, a program file or a dictionary, files on another server, the shared account) are off for a new account and are switched on only by SDSYS. The guide states them so that an agent stops at them. It shows the refusal each one gives, run in an ordinary account, and it teaches no way round any. When one stops an agent, the instruction in the guide is to say which gate it was and to stop; whether to switch it on is for the person who owns the machine.

## What it does not do

It does not make an agent right; it makes the commonest mistakes cheap to avoid. It has not been measured with a model (the plan has a benchmark of thirty tasks, run with and without the guide, and it is not built). It describes SD Core for Linux at its stamp plus the release in progress; items marked 1.2-0 may be missing from a released install and from SD Core Solo for Linux, which has its own pack made from its own sources.
